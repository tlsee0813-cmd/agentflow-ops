# Codex 앱 총괄 하네스 연결 결과

2026-10-23. 기준 Ops main eb4a51850bdefaf804b8558cbb303ed20abd5398에서 작업. 계정 자동 전환은 제외했다. 이 변경은 Ops 운영 환경이며 AgentFlow Studio 제품 수정이 아니다.

## 설치한 것

- 개인 `agentflow-coordinator` 스킬. 로컬 runtime.json으로 기존 Ops checkout과 Node 경로를 찾는다. 제품 프로젝트에서 시작해도 Ops 스크립트는 해당 runtime에서 호출한다. 글로벌 config/AGENTS/로그인 프로필을 교체하지 않았다.
- 총괄의 접수 전 기록, 실제 worker ID, 결과 회수, 채택·통합 절차. 외부 워커에게는 관련 범위만 전달한다. 새로운 큐·상주 서버는 없다.
- DeepSeek 공식 DSH 0.2.1-rc.2의 제한된 headless 워커. 원본 세션·stdin·JSON 결과 기능을 재사용하고 입력 범위와 완료 판정만 얇게 감쌌다. 추출·분류·초안에만 사용한다.

Pro 실제 실행에서 모델 picker GPT-6와 thinking Pro 선택 확인이 남았다. 실행 중 다른 통합 작업을 계속했고 같은 질문을 재전송하지 않았다. 로그 원본은 로컬 비공개 보관, 공개 결정만 아래에 기록한다.

## 발견하고 고친 것

1. 독립 새 문맥 실행에서 `.ops`의 파일은 존재해도 Oracle의 Git ignore 필터로 첨부 실패(exit 1)했다. 공개 요약을 prompt에 넣은 dry-run은 exit 0이었다. 작업 JSON 저장 위치와 첨부 파일 위치의 차이를 스킬·CLI 문서에 명시했다. 비공개 폴더의 ignore를 해제하지 않았다.
2. Pro는 전송 후 접수 ID를 기록하기 전 총괄이 종료되면 복구가 빠질 수 있다고 지적했다. 전송 전 `접수 확인 전` 행을 만들고 ID가 나오면 채우도록 변경했다. 이 기록만으로 exactly-once를 보장한다고 주장하지 않는다.
3. Pro는 모든 명령의 cwd를 Ops로 지정하면 제품 HEAD를 혼동할 수 있다고 지적했다. Ops 스크립트만 Ops에서 실행하고 제품 Git·수정·테스트는 제품 저장소에서 실행하도록 고쳤다.
4. Pro는 전체 result stdout을 다시 읽으면 문맥이 중복된다고 지적했다. 전체 로그는 로컬 파일에 보존하고 종료 상태·결론·필요 구간만 읽도록 예시를 고쳤다.
5. 소스 스킬 수정 중 설치본과 일시적으로 내용이 달랐다. 최종 설치기를 다시 실행하고 원본·설치본 해시 일치와 형식 검사 통과를 확인했다.

## DeepSeek 응답 내용

공개 운영 규약을 입력해 총괄, DSH, 독립 검증의 역할을 분류하게 했다. 실제 답변은 총괄이 목표·범위·선택·충돌 해결·최종 통합을 소유하고, DSH는 좁은 추출·분류·초안만 수행하며, 독립 검증은 중요한 변경에 한 번 배정한다고 구분했다. 제공하지 않은 구체적 절차는 미확인으로 남겼다. 총괄이 입력과 대조해 적합하다고 판단했다.

사용자가 `.ops/dsh-home/.env`에 키를 직접 입력·저장했다. 비밀 값은 출력하거나 GitHub에 전송하지 않았다. 해당 파일과 디렉터리는 현재 Windows 사용자만 접근하는 ACL을 적용했고 Git ignore 대상이다. 결과 JSON과 원본 DSH 세션은 로컬 `.ops`에 있다. 이 공개 기록에는 키나 원본 인증 로그가 없다.

## 남은 한계

- 기존 Ops Cloud durable 환경은 프록시 연결 오류로 최신 GitHub 소스 직접 조회·제품 테스트에 사용할 준비가 안 됐다. 발췌 검토와 로컬 독립 검증으로 구분한다. 다른 제품 Cloud 환경 전체가 실패했다는 뜻은 아니다.
- 새 Codex 앱 세션에서의 스킬 UI 발견, Pro·Claude·DeepSeek를 모두 사용하는 한 제품 변경의 종단간 실행은 아직 별도 실증하지 않았다. 개별 실제 성공을 전체 자동화 완료로 확대하지 않는다.
- 계정 자동 전환은 켜지 않았고 시험하지 않았다. Astra 사용량 감소율도 측정하지 않았다.
