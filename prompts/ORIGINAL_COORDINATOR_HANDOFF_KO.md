# 원래 AgentFlow Studio 총괄에게 전달할 요청

너는 기존 AgentFlow Studio의 제품 총괄이다. 새 총괄에게 넘길 제품 인수인계를 준비해줘. 아래 실행 환경은 이미 별도 Ops 작업에서 구성했으므로 새 총괄에게 다시 만들거나 전체 연결 시험을 반복하라고 하지 마. 지금 제품 개발을 새로 시작하거나 다른 세션에 메시지를 보내는 요청은 아니다.

## 먼저 새 총괄의 환경을 파악해줘

운영 저장소: https://github.com/tlsee0813-cmd/agentflow-ops

최신 main에서 다음 순서로 필요한 것만 읽어라.

1. `docs/STATUS.md`: 실제 준비 상태와 남은 제약.
2. `docs/NEW_CODEX_SESSION_KO.md`, `skills/agentflow-coordinator/SKILL.md`: 새 Codex 앱 로컬 총괄의 시작 방식과 책임.
3. `docs/COORDINATOR_STATE.md`: Ops 작업의 ID·완료 여부. 제품 상태 문서와는 별개다.
4. 계정 관련 설명이 필요할 때만 `docs/ACCOUNT_OPERATIONS_KO.md`의 최신 상태를 확인한다. 실제 전환이 완료됐는지, 설정만 준비됐는지 구분해 인계한다.

새 총괄은 같은 노트북의 Codex 앱 로컬 세션이며 개인 스킬 `$agentflow-coordinator`가 기존 Ops runtime을 가리킨다. API 키·로그인·브라우저 프로필을 넘기거나 복제할 필요가 없다. `docs/SHARED_SETUP_KO.md`에 공통 로컬 환경과 계정별 연결을 구분했다. 저장소 fetch·commit·push는 이미 인증한 로컬 Git을 우선 사용하며, 새 계정에 GitHub connector가 없다는 이유로 전체 환경을 다시 준비하지 않는다. 총괄은 목표·분담·회수·채택 판단·충돌 해결·통합을 맡고, 외부 워커는 관련 자료와 좁은 완료 조건만 받는다.

자동 순환은 Business 두 사용자와 지정 Plus 크레딧 계정만이다. Business가 소진되면 다른 사용 가능한 Business, 없으면 Plus로 옮기고 이어간다. Business 한도가 회복되면 작업 중이어도 Business로 전환·재개한다. 전체 세션 idle 대기는 없고 Pro는 자동 선택에서 제외한다. 설정된 자동 전환의 대상 thread는 제품의 새 총괄과 다를 수 있다. 새 총괄 UUID를 정하기 전에 기존 감시 설정을 복제하거나 다른 대화를 재개하도록 바꾸지 마. 전환·재개의 실제 검증 범위와 대상 변경 절차는 최신 계정 운영 문서를 그대로 인계해라.

실제 Pro → Business 전환과 같은 대화의 자동 재개는 검증됐고, Ops 총괄의 자동 감시는 2026-10-24에 활성화했다. 자연 한도 소진에 따른 전체 계정 순환은 별도 미검증이며 최신 대상·상태는 STATUS를 확인해라. 최신 앱의 턴 구조와 원본 monitor 호환 문제는 Work 자체의 미지원과 다르다. 새 총괄에 연결할 때는 자기 UUID를 확인하고 기존 미해결 전환이 없는지 확인하는 좁은 설정이 필요하다. 이를 환경 전체 재구축이나 외부 로그인 반복으로 확대하지 마.

- Pro: 로그인된 Oracle CLI로 실제 요청과 전체 답변 회수 가능. 실행 부모 세션을 유지하며 기다리는 동안 독립 작업을 진행한다. Oracle sessionId와 실행 도구 session_id, CUA 대화 URL은 서로 다르다.
- Claude Code: 기존 웹 환경에서 좁은 구현을 맡기고 GitHub 커밋/브랜치로 돌려받는다. 실제 원격 HEAD를 확인하며 오래된 로컬 origin/main을 최신이라고 가정하지 않는다.
- DeepSeek/DSH: 로컬 인증과 실제 응답 검증 완료. 좁은 추출·분류·초안에 사용하며 최종 판단이나 도구를 쓰는 구현을 맡기는 경로는 아니다.
- 브라우저: 화면 조사·조작·이미지 확인에 사용한다. Pro·Claude 등 기존 외부 로그인은 총괄 계정 변경과 별개로 유지한다.
- Cloud: Ops에서 시험한 기존 durable 환경에는 프록시 문제가 남아 있다. 이 환경의 최신 GitHub 직접 조회·제품 독립 실행을 가능하다고 배정하지 않는다. 네가 쓰던 다른 Cloud 환경의 상태는 실제 링크·검증 근거로 별도 인계한다. 필요한 검증은 준비된 환경이나 로컬 독립 담당에게 맡긴다.
- 내장 보조: 기본 6.1 Sol high, 어려운 판단만 Astra high. 같은 일을 총괄과 여러 워커가 중복 수행하지 않는다.

새 앱 세션에서 Pro·Claude·DeepSeek 왕복과 IAB 화면 조작을 확인한 공개 근거는 `results/new-session-2026-10-23/RESULT.md`다. 이 성공을 제품 완성이나 계정 자동 전환 성공으로 확대하지 않는다.

## 네가 인계해야 할 것은 제품 맥락이다

너의 기억만으로 작성하지 말고 실제 GitHub의 브랜치·HEAD·PR·현재 상태 문서·진행 중 세션을 대조해라. 로컬 폴더 이름이나 과거 ACTIVE 사본을 최신으로 오해하지 마.

다음 내용을 한 개의 명확한 시작 문서로 정리하고, 상세 이력은 기존 문서로 연결해라.

1. **사용자가 얻으려는 경험과 현재 제품 방향.** PC 중심, 프로젝트 진입 화면과 공간 지도, 층위와 부분 펼치기, 돌아왔을 때 변화와 필요한 판단을 가볍게 파악하는 흐름을 지금 구현과 연결해 설명해라. Dify의 사용성·비율·탐색 메커니즘을 참고하되 목적이 다른 제품임을 유지한다. 긴 검토 보고서가 기본 화면을 차지하지 않도록 한다.
2. **지금 실제로 있는 것.** 기준 저장소/브랜치/SHA, 실행 방법, 제품 소스와 연구 시안·합성 사례의 경계, 배포/체험판 반영 범위를 구분한다. 로컬 미커밋 변경이 있다면 소유자·경로·보존 방법을 기록한다.
3. **결정과 열린 문제.** 채택·보류·기각한 중요한 선택에 짧은 이유와 근거를 붙인다. 방향 문서의 질문 목록을 전부 개발할 목록으로 넘기지 않는다. 사용자 요청, 다른 AI의 제안, 총괄의 판단을 구분한다.
4. **진행 중 작업.** 채널·주제·실제 대화 URL/task ID·기준 SHA·반환 브랜치/PR·현재 상태·다음 회수 동작을 표로 남긴다. 이미 끝난 작업과 접수 불명을 분리한다. 같은 주제의 Pro/Claude 작업을 새 총괄이 중복 제출하지 않게 한다.
5. **검증과 결함.** 작성자 검사, 독립 상태 검사, 실제 화면 조작, 이미지 검토, Dify 비교 평가, 미실행 항목을 구분한다. Dify 비교를 사용자 선호에 맞는 평가 기준으로 쓰되 사람이 실제 사용한 결과라고 표현하지 않는다. 미검증이라는 이유로 제품 작업 전체를 멈추게 하지 말고 필요한 좁은 확인을 지정한다.
6. **다음 작은 완결 흐름.** 우선할 한 작업과 완료 조건, 관련 파일, 먼저 회수할 기존 작업, Pro/Claude/검증/DSH에 나눌 독립 범위를 제시한다. 새 총괄에게 대규모 재조사·전체 재설계부터 시키지 않는다. 최신 조사는 실제 결정에 필요한 차이와 부족한 관점에 집중한다.

공유할 증거는 GitHub에서 회수 가능한 링크로 남겨라. 로컬 ZIP 경로와 해시만 인계하지 않는다. 비밀·로그인·개인 계정 자료·비공개 원문은 올리지 않는다. 오래된 시안과 실패 로그는 필요할 때 찾을 링크로 두고 시작 문서에 전부 복사하지 않는다.

## 최종 산출물

- 제품 저장소에 현재 상태와 충돌하지 않는 인수인계 시작 문서를 저장하고 실제 브랜치·커밋·링크를 알려줘. 기존 ACTIVE 등과 역할이 겹치면 중복 상태표를 늘리지 말고 연결해라. 제품 소스·main·공개 배포는 이 인수인계 때문에 바꾸지 마.
- 새 총괄 세션에 붙여 넣을 시작 프롬프트를 작성해라. `$agentflow-coordinator`, 제품 인수인계 링크, 정확한 기준 브랜치/SHA, 먼저 회수할 작업, 첫 완료 조건이 들어가야 한다.
- 기억하지 못하거나 접근하지 못한 부분은 미확인으로 표시하고 필요한 최소 확인을 적어라. 환경 설치·기존 연결 시험·끝난 연구를 다시 수행할 일반 체크리스트로 채우지 마.
- 새 세션 생성·전송은 하지 말고, 사용자가 전달할 문서와 프롬프트를 반환해라.
